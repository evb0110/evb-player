# Desktop playback

Desktop playback uses libmpv rather than Chromium's HTML media decoders. The browser build retains native browser media elements. The controls share a small media interface; the existing progress file and identifiers are unchanged.

## Why the engine changed

A reported 1080p H.264/AAC MP4 stuttered in EVB Player and macOS Preview but played normally in IINA. Inspection found B-frames, equal packet presentation and decoding timestamps, and no MP4 composition-time (`ctts`) table. Its sequence header advertised only one reorder frame. Enabling software decoding in Chromium did not resolve the cadence issue. Both Chromium decoders reported zero dropped frames while presenting irregular image intervals, so that counter alone was inadequate.

H.264 B-frames require presentation order to differ from decode order. FFmpeg explicitly cautions against assigning PTS equal to DTS when B-frames are involved: [setts documentation](https://ffmpeg.org/ffmpeg-bitstream-filters.html#setts). Chromium's [H.264 decoder](https://github.com/chromium/chromium/blob/main/media/gpu/h264_decoder.cc) uses the sequence header's reorder bound and diagnoses out-of-order output as a broken stream.

IINA delegates decoding and synchronization to libmpv: [MPVController.swift](https://github.com/iina/iina/blob/5c15f815/iina/MPVController.swift). mpv includes timestamp-correction behavior beyond a simple codec switch: [mpv manual](https://mpv.io/manual/stable/#options-correct-pts). Using that engine addresses a class of timing and format compatibility problems without a per-file rewrite or transcoding cache. This does not imply identical codec availability across every operating system and libmpv build.

## Integration

- `vendor/electron-mpv-video` contains the MIT-licensed Node-API and rendering bridge, pinned to upstream commit `4944079b4133715848ea3c3bdaf99742b8c68406`, with local adaptations recorded in `THIRD_PARTY_NOTICES.md`.
- `electron/main.ts` attaches it to the trusted main window. Opening a source must pass the same canonical-path and Library-root authorization as the media protocol. Arbitrary filesystem paths and network URLs are rejected. mpv configuration, scripts, online extractors, external references, and automatic neighboring-file loading are disabled.
- `app/plugins/native-media.client.ts` adapts native playback events and methods to the existing controls. libmpv owns the audio clock, frame scheduling, demuxing, decoding, and timing recovery.
- Windows can transfer GPU surfaces through Electron's [sharedTexture API](https://www.electronjs.org/docs/latest/api/shared-texture). When unavailable, the bridge uses libmpv's software rendering API and a WebGL or Canvas surface. macOS and Linux use decoded frame buffers composited by WebGL or Canvas. If native GPU context creation fails on Windows, Canvas 2D avoids routing software frames through an emulated WebGL stack.
- A render context is destroyed with its own graphics context current, as required by [libmpv's rendering API](https://github.com/mpv-player/mpv/blob/master/libmpv/render.h). Window ownership is captured before destruction so closing the window cannot strand native sessions.
- Main-frame navigation and renderer termination release that renderer's sessions. Repeated reloads must not retain audio players or exhaust the session limit.
- A media load requested while Vue's DOM fragment is detached waits for the element's connection event. It must not be silently dropped before the native session exists. The regression suite explicitly loads a detached element before connecting it.
- Playback commands and property changes use libmpv's asynchronous APIs, which are explicitly safe on its render thread. Calling the synchronous APIs on Electron's rendering thread could stall initialization until mpv's internal deadlock timeout. Windows uses `video-timing-offset=0` to avoid holding Electron's main thread ahead of the audio clock, including in its software fallback. macOS/Linux software playback retains mpv's preparation window on its helper thread, allowing for IPC and scheduling latency before presentation.
- The renderer registers all receiving listeners before a `player:start` handshake enables native delivery. Initialization must not discard file or property events before the consumer is ready. The helper owns its Node event loop. Notifications drain their event queue directly on the JavaScript thread; they do not depend on an additional browser or Node scheduling turn.
- Native wakeup and render callbacks are registered after their Node thread-safe callback functions exist, and unregistered before those functions are released. This prevents initial notifications from being dropped during creation. An isolated software-player probe changed from two blank frames and no events to 119 frames and 255 events, including `file-loaded`, after this ordering was repaired.
- `scripts/build-native.mjs` compiles the bridge and stages its runtime dependencies outside the app archive. macOS library install names and Linux rpaths resolve to that private directory. The build checks the relocated module with its bundled Node executable, exercising the dependency loader as well as validating library signatures. Release CI signs and notarizes the complete macOS bundle.
- macOS releases use the pinned, checksum-verified IINA 1.4.4 playback runtime. Its Apple Silicon libraries target macOS 12 rather than inheriting the Homebrew build host's macOS version; the app requires macOS 13.5, matching the bundled Node helper's deployment target. Universal libraries are reduced to the packaged architecture.
- macOS and Linux run libmpv in a bundled ordinary Node helper process. This prevents Electron's FFmpeg ABI and allocator symbols from interposing on native playback. Commands and events use JSON IPC; raw frame bytes use a separate pipe, avoiding V8 serialization-version coupling between Electron and Node; session destruction waits for the helper to exit. The renderer's source authorization remains in Electron's main process.
- The helper renders directly from mpv's update notifications and pushes bounded frames to Electron. A viewport change requests a fresh frame; ordinary playback avoids a control round trip through Electron before rendering each image. Pipe backpressure bounds the producer, and Electron retains only its latest unconsumed frame.
- Active macOS playback declares a user-initiated process activity, following Apple's [App Nap guidance](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheAppLevel.html). Pause, stop, completion and destruction release it. The declaration allows idle system sleep and does not persist after playback.
- Native playback also owns Electron power assertions: video prevents display sleep, and audio prevents application suspension. Pause, stop, completion, process failure and session destruction release them. This replaces Chromium's automatic media wake locks, which are absent when displaying decoded frames on a canvas.
- The dedicated macOS helper initializes mpv with user-initiated thread quality of service, then renders with user-interactive quality of service, matching IINA's [controller](https://github.com/iina/iina/blob/5c15f815/iina/MPVController.swift) and [render queue](https://github.com/iina/iina/blob/5c15f815/iina/ViewLayer.swift). Its playback activity and Electron wake locks remain scoped to playing sessions.
- Windows bundles libmpv's Vulkan loader dependency so a system Vulkan SDK is unnecessary. The software renderer passes its row stride as `size_t`, the width required by libmpv's API on 64-bit systems; an `int` there causes out-of-bounds writes. The detached-element check also exercises software rendering on GPU-equipped hosts.

## Regression evidence

`scripts/test-playback.mjs` synthesizes H.264 with B-frames and deliberately broken `PTS=DTS`. Each decoded image has increasing luminance, allowing the test to detect backwards displayed images rather than merely checking that playback time advances. It also checks exact seeking, speed changes, common non-browser codecs, audio, the native source boundary, and the unchanged progress format.

Automated fixtures use mpv's null audio output, while retaining audio decoding and clocking. They neither require a hosted sound device nor play test tones on the user's desktop; physical audio-output quality is not measured by this suite.

Real user media remains outside the repository. All automation uses generated fixtures or explicitly supplied media read-only, task-owned profiles, and hidden app copies.

The same generated timing sample, played through Chromium for comparison with `EVB_PLAYER_TEST_ENGINE=chromium pnpm test:playback`, produced 13 backwards image transitions and failed the ordering assertion. The libmpv path produced none. This comparison measures displayed image order, independently of decoder drop counters.
